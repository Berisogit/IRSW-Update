# Architectural Decision Record: ADR-001

## Multi-Tenant Cloud-Native Data and Sync Architecture 

* **Status**: Approved
* **Date**: 2026-06-07
* **Owner**: Architecture Team / Lead Developer

---

## 1. Context & Architectural Decision

To coordinate a restaurant’s front-of-house (table QR scanning, waiter ordering) and back-of-house (kitchen display systems, inventory stock updates) seamlessly, we must select an dynamic datastore state engine. 

### Decision
We have decided to build IRSW as a **fully client-driven, serverless SaaS architecture using Cloud Firestore as the primary real-time synchronization database**. 

By adopting a Repository Pattern implemented under `/services/repository.ts` and `/services/firestoreService.ts`, data flow is strictly decoupled from local state variables. Rather than implementing heavy, custom backend API proxy endpoints for REST states, the React UI creates straight-to-Firestore listeners (`onSnapshot`) via tenant scope paths.

---

## 2. Rationale

1. **Sub-second Operational Latency**: Restaurant operations (e.g., sending an order from Table 4 to the kitchen displays) require immediate alerts. Traditional polling-based designs introduce lag or excessive server overhead. Firestore’s direct event subscription natively delivers updates to subscribers within milliseconds.
2. **Serverless Scale & Maintenance**: Running standard relational servers and API web layers increases operations cost and scaling bottlenecks. Embellishing state management via a client-connected serverless pattern scales instantly from single-site operations to multi-tenant operations.

---

## 3. Advantages

* **Declarative Data Synchronization**: The applet declares its reactive bindings once during mounting, automatically feeding updates (like menu edits, tables occupancy, or order workflow progress) down the React layout engine.
* **Optimized Offline Capability**: Built-in cache persistence allows devices like kitchen screens to continue handling local requests during brief networking or connectivity interruptions, synchronizing queue updates automatically when connection is restored.
* **Low Server Maintenance Costs**: Decoupling the operations from secondary servers shrinks hosting footprints. Out-of-the-box infrastructure is managed globally by Google's scalable architectures.

---

## 4. Limitations & Mitigations

* **Vulnerability to Read-Heavy Billing**: Firestore charges primarily on documentation reads. 
  * *Mitigation*: Dynamic layout logic binds listeners to exact filter/query contexts and caches collection lists using local memoized providers so that standard screen re-renders do not invoke secondary read actions.
* **Complex Multi-Joint Queries**: Firestore is a non-relational database. Multi-table joins are slow.
  * *Mitigation*: Maintain localized denormalization (e.g., nesting related array structures inside document models) to represent immediate operational scopes directly.

---

## 5. Multi-Branch & SaaS Organization Strategy

IRSW implements a strict structural separator for organizations:
* Every user, staff member, and core record is tagged with an `organizationId`.
* Real-time listeners bind strictly to scoped collections: `/organizations/{organizationId}/menuItems`, `/organizations/{organizationId}/orders`, etc.
* Cross-tenant query infiltration is physically blocked both at the client interface layer and fortified through custom Firestore Security Rules written in `firestore.rules`.

---

## 6. BigQuery & Analytics Strategy

As the platform matures and organizations request heavy reporting (sales graphs, average table turnover, historical stock depletion), we will integrate a passive real-time data copy stream:

```
[Cloud Firestore] ---> [Cloud Firestore BigQuery Extension] ---> [Google BigQuery]
```

* **Rationale**: Standard Firestore queries are poorly suited for massive analytical aggregations. Doing so on-the-fly inside the client or over separate REST scripts risks exceeding pricing and performance margins.
* **Adoption**: The direct Cloud Firestore BigQuery Extension will automatically mirror collections into BigQuery datasets in real-time, enabling administrators to execute complex SQL reports without degrading active operations.

---

## 7. AI Forecasting Strategy

BigQuery metrics datasets will feed modern Gemini-driven Machine Learning pipelines:
* **Demand Estimation**: Historical restaurant receipts analyzed on BigQuery will train predictive metrics models to estimate category and raw item volumes based on upcoming events, seasonality, holidays, and weather.
* **Automated Stock Procurements**: Predict stock depletions before they interrupt floor service, auto-generating vendor restock tickets to prevent back-of-house shortages.

---

## 8. Security Model

Security guidelines are built around **least-privilege runtime authorizations**:
1. **Firestore Security Rules**: Explicit constraints demand that incoming payloads bear an authenticated token matches the targeted path's tenant parameter: `request.auth.token.organizationId == organizationId`.
2. **Role Validations (RBAC)**: Interface layers check user claims (e.g., `Admin`, `POS`, `Chef`) prior to enabling configuration or audit modification routes.

---

## 9. Future Constraints

* All core structural updates MUST utilize atomic write batch routines (`writeBatch()`) rather than sequential write calls to guarantee that connection failures mid-write never trigger a partial-state corrupt schema database error.
* Code paths MUST never default to local design fallback lists once a user has successfully authenticated.
